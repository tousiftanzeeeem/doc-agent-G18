## What "chunking" means here

You've got it almost right, but one nuance matters: chunking isn't about grouping text by *relevance* — it's about grouping text by *size*, so each piece is small enough to embed and retrieve precisely, but large enough to contain a coherent unit of meaning.

Here's the flow right before chunking, per `pipeline.py`:

```

chunk.split(text, cfg) → chunks            # this is what you're implementing
```

Look at `contracts.py`'s `Chunk` model:

```python
class Chunk(BaseModel):
    id: str
    doc_id: str
    text: str
    page_ids: list[str]
    score: float = 0.0
```

So `ocr.py`'s output is **already** a `list[Chunk]` — one `Chunk` per detected *region* (a paragraph, a table cell, a heading — whatever `layout.py` segmented). These are OCR-shaped chunks, not retrieval-shaped chunks. They could be too big (a whole page-length region) or too small (a 3-word heading) for good embedding/retrieval.

**`chunk.split()`'s job is to re-chunk those region-level pieces into retrieval-sized pieces**, governed by your config:

```yaml
index: {type: "faiss:hnsw", chunk_tokens: 256, overlap: 32}
```

So concretely: take the region text (possibly concatenated in reading order across a page/doc), split it into ~256-token windows with 32-token overlap between consecutive windows, and emit new `Chunk` objects — each with a fresh `id`, the same `doc_id`, and `page_ids` tracking which original page(s) it came from (important for citations later).

## Why overlap, and why token-sized windows (not "by relevance")

- **Fixed-size windows** (the baseline, what your config's `chunk_tokens`/`overlap` implies) ensure every chunk fits your embedding model's context and gives retrieval consistent granularity — too big and a chunk mixes multiple topics (bad precision); too small and it loses context (bad recall).
- **Overlap** prevents a sentence or fact from being cut in half at a chunk boundary and losing meaning in both halves.
- **"By relevance"** is actually a different, more advanced strategy — semantic/paragraph chunking (splitting at natural topic boundaries instead of a fixed token count). Your codebase guide flags this as an *upgrade path* (`E4 — paragraph/semantic chunking (better retrieval) → index/chunk.py`), not the baseline. Worth knowing about, but not required first.

## What you actually need to write

`split(chunks: list[Chunk], cfg: dict) -> list[Chunk]`:
1. For each input `Chunk` (or concatenated per-doc/per-page text), tokenize it.
2. Slide a window of `cfg['index']['chunk_tokens']` tokens, stepping by `chunk_tokens - overlap` each time.
3. For each window, create a new `Chunk` with a new unique `id`, same `doc_id`, and `page_ids` set to whichever original page(s) that window's text came from.
4. Return the flattened list of these new chunks.

One design decision you'll want to note in `design_choices.md`: do you re-chunk **within each region independently**, or **concatenate all regions on a page/doc first, then chunk across region boundaries**? The latter gives better recall on facts that span two OCR'd regions, but risks mixing unrelated content (e.g., a heading bleeding into unrelated table text). That's a legitimate design call to make and justify.

## 2. When does tokenization actually happen?

Good catch — this is the part that's easy to get confused about. Tokenization in `split()` is a **transient/internal step**, not something that changes the `Chunk` object's shape.

`Chunk.text` is a plain Python string, always. It goes in as a string and comes out as a string. What happens *inside* `split()` is:

1. Take `chunk.text` (a string) → run it through a tokenizer → get a list of tokens (usually integers, or token strings, depending on the tokenizer).
2. Slide a window over that token list (e.g. take tokens `[0:256]`, then `[224:480]`, etc. — note the overlap).
3. **Decode each window back into a string** (or, if you tokenized to strings, just re-join them).
4. Wrap that decoded string into a new `Chunk(text=..., id=..., ...)`.

So tokenization is just how you *measure and cut* the text — a ruler, not a transformation of the data itself. The reason you can't just cut on whitespace or characters is that "256 tokens" is what your **embedding model** actually cares about — embedding models have a max input length measured in *their* tokens, and retrieval quality depends on staying inside a size that the embedder handles well. Character or word counts don't map cleanly to that.

## 3. Do you write a tokenizer?

No — you should **not** write a tokenizer from scratch. Use one that already exists, and ideally the *same* one your embedding model uses, so "256 tokens" in `chunk.py` means the same thing as "256 tokens" to `embed.py`.

Your config has:

from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")

This is the "correct" approach because it keeps `chunk_tokens: 256` consistent with what the embedder will actually see. A cheaper fallback some teams use for a first pass is whitespace-splitting (`text.split()`) as a rough proxy for tokens — faster, less accurate, but fine as a baseline you can later swap out. Worth deciding and noting which you pick in `design_choices.md`.

## 4. Within-region vs. concatenate-then-chunk

**Within-region**, yes exactly what you said: `chunks[0].text` gets windowed into however many sub-chunks it needs on its own, independently, then `chunks[1].text` gets windowed into its own sub-chunks, and so on. Region boundaries are never crossed — a chunk from region 0 will never contain any text from region 1, even if region 0 is very short.

**Concatenate-then-chunk**: you'd join the text of all regions on a page (or doc) together, *in reading order*, into one long string first, and then slide the 256-token window over that combined string — so a window can span the tail of region 0 and the head of region 1.

Your last question is the sharp one: **if we're going to concatenate regions back together anyway, what was the point of running OCR on each region separately?**

The answer: **layout detection and per-region OCR is about transcription quality, not chunking granularity — those are two separate concerns.** Feeding the OCR `Reader` a whole cluttered page image (with a table, a figure, a heading, and two text columns all mixed together) produces much worse transcriptions than feeding it one clean, cropped, single-purpose region at a time — the model doesn't get confused about reading order, doesn't try to read table cells as flowing prose, doesn't hallucinate text over a figure. Per-region OCR is what makes the *text itself* accurate.

Once you have that accurate text, what you do with it for chunking is a completely separate decision — you're free to stitch region texts back together in reading order before windowing, without losing anything you gained from doing OCR region-by-region. In fact you'd typically also *use* the region's `kind` (from `Region.kind`: text/table/figure/heading) at concatenation time — e.g. skip figures, keep tables as their own atomic chunks rather than letting them get windowed mid-table, only concatenate consecutive `text`-kind regions.

So a reasonable real design: OCR per region (quality) → concatenate same-kind consecutive text regions per page in reading order → then apply the 256/32 sliding window over that (chunking granularity for retrieval) → keep table/figure regions as separate whole chunks rather than windowing them.

"""Stage 4 — chunk text"""
from __future__ import annotations
from ..contracts import *  # noqa
from transformers import AutoTokenizer
# Loaded once per process, keyed by model name, so we don't reload on every call.
_tokenizer_cache: dict[str, "AutoTokenizer"] = {}
def _get_tokenizer(cfg: dict):
    model_name = cfg["embed"]["model"]
    if model_name not in _tokenizer_cache:
        _tokenizer_cache[model_name] = AutoTokenizer.from_pretrained(model_name)
    return _tokenizer_cache[model_name]
def split(chunks: list[Chunk], cfg: dict) -> list[Chunk]:
    """Re-chunk to cfg['index'] size/overlap.
    Each input Chunk (one OCR'd layout region) is windowed independently:
    region boundaries are never crossed. Uses the embedding model's own
    tokenizer so 'chunk_tokens' means the same thing here as it will to embed.py.
    """
    tokenizer = _get_tokenizer(cfg)
    chunk_tokens = cfg["index"]["chunk_tokens"]
    overlap = cfg["index"]["overlap"]
    stride = chunk_tokens - overlap
    assert stride > 0, "overlap must be smaller than chunk_tokens"
    out: list[Chunk] = []
    for region_chunk in chunks:
        token_ids = tokenizer.encode(region_chunk.text, add_special_tokens=False)
        # Region already fits in one window -> keep as-is (still re-wrapped for a fresh id).
        if len(token_ids) <= chunk_tokens:
            out.append(Chunk(
                id=f"{region_chunk.id}-0",
                doc_id=region_chunk.doc_id,
                text=region_chunk.text,
                page_ids=region_chunk.page_ids,
            ))
            continue
        start = 0
        window_idx = 0
        while start < len(token_ids):
            end = min(start + chunk_tokens, len(token_ids))
            window_ids = token_ids[start:end]
            window_text = tokenizer.decode(window_ids, skip_special_tokens=True)
            out.append(Chunk(
                id=f"{region_chunk.id}-{window_idx}",
                doc_id=region_chunk.doc_id,
                text=window_text,
                page_ids=region_chunk.page_ids,
            ))
            if end == len(token_ids):
                break
            start += stride
            window_idx += 1
    return out

## What normalization actually does
Right now, `model.encode()` with `normalize_embeddings=True` takes whatever raw 384-number vector the model produces and rescales it so its **length (magnitude) becomes exactly 1**, while keeping its **direction** unchanged. Geometrically: instead of landing anywhere in 384-dimensional space, every vector gets pulled/pushed to sit exactly on the surface of a unit hypersphere.
Think of a simpler 2D analogy: a vector like `(3, 4)` has length 5 (by Pythagoras). Normalizing it means dividing every component by that length, giving `(0.6, 0.8)` — same direction (same angle from the origin), but now length exactly 1.
## Why this matters for retrieval
There are two common ways to measure "how similar are two vectors":
- **Cosine similarity** — only cares about the *angle* between two vectors (their direction), ignoring how long each one is.
- **Dot product** — cares about *both* angle AND length. A vector with a bigger magnitude will score higher on dot product even if it points in a similar direction, purely because it's "longer."
Here's the key mathematical fact: **if both vectors are already normalized to length 1, dot product and cosine similarity give the exact same result.** Normalizing removes magnitude entirely from the equation, so all that's left to compare is direction — which is exactly what "meaning similarity" should be measuring.
## Why that's the right choice for you
Your config has:
```yaml
retrieve: {k: 10, ..., weak_threshold: 0.35, ...}
```
`retrieval/retriever.py` will need to score "how relevant is this chunk to the query" using *some* similarity function. If embeddings are normalized, that scoring step (and libraries like FAISS) can use a plain, fast dot product and get correct cosine-similarity behavior for free — no separate normalization step needed at query time either (as long as the query is embedded and normalized the same way).
If embeddings were **not** normalized, you'd have a subtle bug risk: a longer chunk of text, or text with more "salient" tokens, might just naturally produce a larger-magnitude vector — and that chunk could get ranked as "more similar" to the query not because its *meaning* actually matches better, but purely because its vector happens to be longer. Normalization removes that magnitude-driven bias, so ranking is driven by direction (semantic similarity) alone.
## The tradeoff / what you lose
You do lose *some* information — magnitude *can* occasionally carry a weak signal (e.g. very short, sparse, ambiguous text sometimes produces smaller-magnitude embeddings from certain models, so magnitude is occasionally usable as a rough "confidence"/specificity signal). But for retrieval-by-similarity use cases like this project, that signal is minor and unreliable compared to the benefit of a clean, consistent similarity metric — so normalizing is the standard, safe default for `sentence-transformers` models being used for semantic search (it's what the model's own documentation recommends for this exact use case).
**Bottom line:** normalizing means "compare chunks by meaning-direction only, ignore vector length" — which is what you want for finding the most relevant chunks to a query, and it keeps `retriever.py`'s similarity math simple (plain dot product) later. This is a decision worth writing down explicitly in `design_choices.md`, since `retriever.py`'s eventual implementation depends on it matching.
