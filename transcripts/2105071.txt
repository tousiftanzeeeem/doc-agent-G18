Now reading order. I have sorted(boxes, key=lambda b: (b[1], b[0])) which works for pure single-column but I was told this corpus has dense statistical tables where multiple boxes sit side by side?

AI: Right, a global (y, x) sort will interleave side-by-side table cells with text blocks at similar y-positions. A cheap fix is a **banded sort**: group boxes into horizontal rows based on y-position relative to the median box height, sort each row left→right, then stack rows top→bottom.

```python
med_h = float(np.median([b[3] for b in boxes]))
bands = {}
for b in boxes:
    band = int(b[1] // max(med_h, 1))
    bands.setdefault(band, []).append(b)
ordered = []
for band_key in sorted(bands):
    ordered.extend(sorted(bands[band_key], key=lambda b: b[0]))
```

This is deterministic (important for the reproducibility gate) and keeps within-row order correct for tables.

AI: The issue is that `assert` statements in Python are stripped when running with the `-O` (optimize) flag. Bandit flags them because using `assert` for validation that should *always* run — like checking that a seam name is valid — is unreliable in production. If someone runs `python -O pipeline.py`, the assert silently disappears and invalid seam values would pass through uncaught.

The fix is to replace:
```python
assert seam in SEAMS
```

with an explicit if-check that raises a proper exception:
```python
if seam not in SEAMS:
    raise ValueError(f"Unknown seam: {seam!r}. Valid seams: {SEAMS}")
```

This has three advantages:
1. It runs regardless of optimization flags
2. It gives a clear error message (the assert version just says `AssertionError` with no context)
3. Bandit won't flag it
